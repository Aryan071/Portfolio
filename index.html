Atlas Distributed search engine

A search engine I wrote from scratch in Python, with its own inverted index, BM25 ranking, and a coordinator that keeps results correct across shards.

  • 0throughput on 4 shards
  • 0lower p95 latency
  • 0errors in shard-kill drill
Case study
Problem
If every shard ranks with its own statistics, the same query gives scores that cannot be compared across shards.
Approach
A two-phase query: the coordinator first collects global term statistics, then every shard scores with them. Documents are hash-partitioned across shards, Kafka feeds ingestion, and a cache serves hot queries.
Result
2.7x throughput and 3.3x lower p95 latency on 4 shards versus 1 (8 clients, 100K documents, one machine, synthetic data). Zero request errors when a shard was killed under load; results were flagged as partial. Read the write-up.

2026

TraceLens Production-to-code intelligence

Ask "why is this endpoint slow after the deploy?" and get an answer from evidence: OpenTelemetry traces, a code index and git history joined by a correlation engine, shown in VS Code.

  • 0spans per second ingested
  • #1guilty commit ranked first in demo runs
  • 0rejections at load
Case study
Problem
When production slows down or breaks, finding the commit responsible usually means searching logs and git history by hand.
Approach
Traces go into ClickHouse; a code index and deployment records go into PostgreSQL. A deterministic engine compares releases, maps slow queries back to the line of code, and ranks commits. An LLM may phrase the result, but every claim must cite evidence.
Result
About 49K spans/s accepted when 50K are offered to 4 processes, with 0 rejections (one process tops out near 24K). In the demo scenarios the guilty commit ranked #1. Read how I measured it.
