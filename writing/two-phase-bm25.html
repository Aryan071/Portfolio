Why BM25 scores from different shards can't be compared

When I split Atlas, my search engine, across shards, the same query produced rankings that looked fine and were wrong. The cause is one term in the formula. The fix is a second round trip.

The problem in one sentence

BM25 multiplies a term's IDF (how rare the term is) by a term-frequency part. IDF depends on two collection-wide numbers: N, the number of documents, and df, how many of them contain the term. A shard only knows its own N and df.

A tiny example

Take the term "raft". Shard A holds 10 documents and 1 of them contains it. Shard B holds 1,000 documents and 1 of them contains it. Use Lucene-style IDF, ln(1 + (N - df + 0.5) / (df + 0.5)):

NdfIDFScore of a doc with tf=2
Shard A (local)1011.992.74
Shard B (local)1,00016.508.94
Global (both shards)1,01026.008.25

The two documents are equally relevant, but the one on shard B scores more than three times higher, only because its shard is bigger. If the coordinator merges the shards' top results by score, shard B wins for the wrong reason. (Scores use k1 = 1.2, b = 0.75 and a document of average length.)

The fix: a two-phase query

  1. Phase A, statistics. The coordinator asks every shard for its N, the df of each query term, and field lengths. It adds them up to global statistics.
  2. Phase B, scoring. The coordinator sends the query and the global statistics to every shard. Each shard scores with the same IDF and returns its top results.
  3. Merge. Now scores are comparable. The coordinator merges by score descending, then by document ID ascending, so ties are deterministic.
async def search(q, limit=10):
    stats = await gather(*(s.stats(q) for s in shards))   # phase A
    g = merge_stats(stats)                                 # N, df, lengths
    hits = await gather(*(s.score(q, g) for s in shards))  # phase B
    return top_k(hits, limit)                              # score desc, id asc

What it costs

One extra round trip per query. In my benchmark (4 shards versus 1, 8 concurrent clients, 100,000 documents, one laptop, synthetic data) the sharded setup still reached 2.7x the throughput and 3.3x lower p95 latency, so the extra phase paid for itself. The numbers come from the benchmark notes in the Atlas repository, and they describe that setup only: the coordinator becomes the bottleneck before the shards do, and my own p95 target of 200 ms is not met under concurrency at that size.

What I would do differently

  • Cache the global statistics per index generation instead of fetching them for every query. (Atlas already keys its result cache by generation.)
  • Add consistent hashing so resharding does not need a full rebuild.
